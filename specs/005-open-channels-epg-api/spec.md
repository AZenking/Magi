# Feature Specification: 开放接口平台 — 频道与节目单只读 API

**Feature Branch**: `005-open-channels-epg-api`

**Created**: 2026-07-29

**Status**: Draft

**Input**: User description: "构建一个通用开放接口平台(Open API),让任意客户端(含 Android TV、第三方、脚本)凭 API key 只读访问「频道列表」和「节目单」。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员签发 API key 供外部客户端使用 (Priority: P1)

管理员希望为某个外部消费方(如客厅的 Android TV、一个数据导出脚本、一个第三方自建播放器)签发一把独立的访问凭据,以便该消费方可以读取 Magi 整理后的频道和节目单数据,而无需借用管理员浏览器登录态。签发时明文凭据只显示一次,管理员需立即复制保存。

**Why this priority**: 这是整个开放平台的前提 —— 没有凭据签发能力,任何客户端都无法接入。它是其他所有故事的基础。

**Independent Test**: 管理员登录后台,在「开放接口」页创建一把名为"客厅电视"的 key,看到一次性显示的明文凭据并复制;随后在列表中看到该 key(以打码前缀显示)、状态为启用。可独立于"客户端实际调用"完成验证。

**Acceptance Scenarios**:

1. **Given** 管理员已登录后台且至少存在一个有效频道,**When** 管理员创建一把名为"客厅电视"的 API key,**Then** 系统一次性返回完整明文凭据,且管理员能在列表中看到该 key 的打码前缀与"启用"状态。
2. **Given** 一把已签发的 API key,**When** 管理员在列表再次查看或刷新页面,**Then** 系统不再显示明文凭据,仅显示打码前缀。
3. **Given** 一把已签发的 API key,**When** 管理员对其执行"禁用",**Then** 该 key 状态变为"禁用",使用它的外部客户端立即无法再读取数据。

---

### User Story 2 - 外部客户端凭 key 读取频道列表 (Priority: P1)

一个持有有效 API key 的外部客户端(脚本、自建播放器、Android TV)希望拉取 Magi 整理后的频道列表,按分组浏览或搜索特定频道,用于本地展示或下游处理。客户端只关心"对外的产品视图"(频道名、分组、台标、频道号),不需要知道上游线路、健康详情等内部运维信息。

**Why this priority**: 频道列表是开放接口的核心数据交付,是大多数消费方的首要需求。与 US1 并列 P1,二者共同构成最小可用闭环。

**Independent Test**: 用一把有效 key 调用频道列表与频道详情接口,返回的数据只包含产品视图字段、不含上游地址,即可验证。

**Acceptance Scenarios**:

1. **Given** 一把状态为"启用"的 API key 且系统存在至少一个对外可见频道,**When** 客户端携带该 key 请求频道列表,**Then** 系统返回分页的频道数据,每条频道包含稳定标识、标准名称、分组、台标、频道号。
2. **Given** 同一把 key,**When** 客户端按分组名称过滤或按关键词搜索,**Then** 系统仅返回符合条件的频道。
3. **Given** 一个对外不可见的频道(已隐藏/停用/回收),**When** 客户端请求频道列表或其详情,**Then** 系统不返回该频道。
4. **Given** 一次频道列表或详情响应,**When** 审查其字段,**Then** 响应中不包含上游播放地址、原始来源标识、线路健康状态、内部生命周期标记等运维字段。

---

### User Story 3 - 外部客户端凭 key 读取节目单 (Priority: P2)

持有有效 API key 的外部客户端希望在指定时间窗口内读取节目单(EPG),以展示"当前节目 / 下一节目 / 当日时间轴",支撑节目预告和节目详情展示。客户端只读取与对外频道关联的节目数据。

**Why this priority**: 节目单是仅次于频道列表的高频数据需求,但消费方可仅凭频道列表先跑起来,因此优先级低于 US2。

**Independent Test**: 用有效 key 指定一个合理时间范围请求节目单接口,返回节目带起止时间且仅关联对外频道,即可验证。

**Acceptance Scenarios**:

1. **Given** 一把"启用"的 API key 且存在已绑定 EPG 的对外频道,**When** 客户端携带起止时间请求节目单,**Then** 系统返回该时间窗内与对外频道关联的节目(标题、起止时间、分类)。
2. **Given** 同一把 key,**When** 客户端请求的时间窗超过系统允许的最大跨度,**Then** 系统拒绝并返回明确的错误提示。
3. **Given** 一个对外不可见的频道,**When** 客户端请求其节目单,**Then** 系统不返回该频道的节目。

---

### User Story 4 - 开发者凭 OpenAPI 契约自助接入 (Priority: P2)

第三方开发者或脚本作者希望在不知道内部实现的前提下,通过一份机器可读的接口契约(OpenAPI 规范)理解开放接口的能力、参数与响应结构,甚至据此生成客户端代码,从而自助完成接入,无需向 Magi 维护者逐个询问字段含义。

**Why this priority**: 契约文档是"开放"的语义核心 —— 没有它,接口虽能调但不算真正"开放"。与 US3 并列 P2。

**Independent Test**: 访问交互式文档与机器可读规范地址,二者内容一致且覆盖所有开放端点,即可验证。

**Acceptance Scenarios**:

1. **Given** 开放接口已部署,**When** 开发者访问交互式接口文档地址,**Then** 看到所有开放端点、参数、响应结构与错误说明。
2. **Given** 同一部署,**When** 开发者获取机器可读的接口规范文件,**Then** 该规范与交互文档描述一致,且能被标准工具解析校验。
3. **Given** 该规范文件,**When** 开发者用标准工具生成客户端代码,**Then** 生成的客户端类型与实际响应结构匹配。

---

### User Story 5 - 管理员吊销与清理 API key (Priority: P3)

当一把 key 泄露、对应的客户端不再使用、或管理员希望轮换凭据时,管理员需要能吊销(永久失效)或删除 key,并在事后可追溯是谁、何时操作了这把 key。

**Why this priority**: 运维与安全收尾能力,不影响首发可用性,但正式运营前必须有。

**Independent Test**: 吊销一把 key 后,原客户端立即无法访问;且审计记录可查,即可验证。

**Acceptance Scenarios**:

1. **Given** 一把"启用"的 key,**When** 管理员执行"吊销",**Then** 该 key 永久失效,使用它的客户端立即被拒绝,且列表状态更新为"已吊销"。
2. **Given** 任一对 key 的管理操作(创建/禁用/启用/吊销/删除),**When** 管理员事后查阅审计,**Then** 能看到操作者、操作类型与时间。
3. **Given** 一把已吊销或已删除的 key,**When** 客户端尝试用它访问,**Then** 系统拒绝并返回未授权错误。

### Edge Cases

- 客户端请求未携带任何凭据,或凭据格式错误(非 `Bearer ` 前缀、非预期前缀)时,系统如何响应?→ 返回未授权错误,不泄露凭据是否曾经存在。
- 凭据正确但状态为"禁用"/"已吊销"/"已删除"时,系统如何响应?→ 统一返回未授权错误(不区分具体失效原因,避免被探测)。
- 凭据设有过期时间且已过期时?→ 视同失效,返回未授权。
- 频道列表为空(无任何对外可见频道)时?→ 返回空分页结果(正常 200),而非错误。
- 节目单请求的时间窗起始晚于结束、或参数格式非法时?→ 返回参数校验错误。
- 某个 key 被高频调用(疑似脚本失控或滥用)时?→ 超出限流阈值时返回限流错误,而非拖垮系统。
- 外部客户端尝试用 key 访问仅限管理员的后台管理接口时?→ 被拒绝(凭据类型隔离)。
- 管理员浏览器登录态尝试访问开放接口时?→ 同样被拒绝(凭据类型隔离)。

## Requirements *(mandatory)*

### Functional Requirements

**凭据管理(管理员侧)**

- **FR-001**: 系统 MUST 允许已登录管理员创建一把命名的 API key,并在创建时一次性返回完整明文凭据。
- **FR-002**: 系统 MUST 在创建后以不可逆方式存储凭据摘要,任何后续查询都不得返回明文,列表展示仅显示打码前缀。
- **FR-003**: 系统 MUST 允许管理员列出所有 API key,每条展示名称、打码前缀、状态、最近使用时间、创建时间。
- **FR-004**: 系统 MUST 允许管理员对 key 执行启用、禁用、永久吊销与删除操作,且状态变更立即对正在使用该 key 的客户端生效。
- **FR-005**: 系统 MUST 对每一笔凭据管理操作(创建/禁用/启用/吊销/删除)记录审计:操作者、操作类型、目标 key、时间。
- **FR-006**: 系统 MUST 允许为 key 设置可选的过期时间;过期后该 key 自动视为失效。

**数据访问(开放接口侧)**

- **FR-007**: 开放接口 MUST 仅在请求携带有效且未失效凭据时放行;否则返回未授权错误,且不泄露凭据是否曾经存在。
- **FR-008**: 开放接口 MUST 提供频道分组查询,返回各分组名称及其频道数量。
- **FR-009**: 开放接口 MUST 提供分页的频道列表查询,支持按分组过滤与按关键词搜索。
- **FR-010**: 开放接口 MUST 提供单个频道详情查询。
- **FR-011**: 开放接口 MUST 仅返回对外可见的频道(已隐藏/停用/回收的频道不得出现在任何响应中)。
- **FR-012**: 开放接口的所有频道响应 MUST 只包含产品视图字段(稳定标识、标准名称、分组、台标、频道号),且 MUST NOT 包含上游播放地址、原始来源标识、线路健康详情、内部生命周期状态等运维字段。
- **FR-013**: 开放接口 MUST 提供节目单查询,按起止时间窗返回与对外频道关联的节目。
- **FR-014**: 系统 MUST 对节目单查询的最大时间跨度施加上限,超出时拒绝并返回明确错误。
- **FR-015**: 开放接口的稳定频道标识 MUST 与现有对外输出使用的稳定标识保持一致,以便客户端跨接口复用。

**契约与隔离**

- **FR-016**: 系统 MUST 提供机器可读的开放接口规范文件(OpenAPI 格式),覆盖所有开放端点的参数与响应结构。
- **FR-017**: 系统 MUST 提供基于该规范的交互式接口文档。
- **FR-018**: 开放接口规范文件 MUST 与交互式文档描述一致,且可被标准工具解析校验。
- **FR-019**: 开放接口鉴权 MUST 与后台管理员登录态鉴权相互隔离 —— 管理员登录态 MUST NOT 能访问开放接口,API key 凭据 MUST NOT 能访问后台管理接口。
- **FR-020**: 系统 MUST 对开放接口施加按凭据的调用频率限制,超出时返回限流错误而非拒绝服务。

**可观测与安全**

- **FR-021**: 系统 MUST NOT 在任何日志中记录 API key 的明文。
- **FR-022**: 开放接口请求 MUST 携带可追溯的链路标识,与现有请求链路机制一致,便于跨服务排查。

### Key Entities *(include if feature involves data)*

- **API Key(访问凭据)**: 代表一个外部消费方的访问身份。关键属性:名称、凭据摘要(不可逆)、打码前缀、状态(启用/禁用/已吊销)、过期时间、预留的作用域、最近使用时间、创建者、创建时间。关系:由管理员创建,可关联零到多次开放接口调用。
- **对外频道(产品视图)**: 从系统已整理的频道数据中投影出的对外可见频道。关键属性:稳定标识、标准名称、分组、台标、频道号。它不是新的数据源,而是对现有整理后频道的受限投影。
- **对外节目(产品视图)**: 与对外频道关联的节目。关键属性:标题、起止时间、分类。同样是对现有节目数据的受限投影。
- **审计事件**: 记录凭据管理操作的不可变痕迹。关键属性:操作者、操作类型、目标、时间。复用现有审计能力。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员能在 1 分钟内为一个新的外部消费方签发一把可用的 API key,并在创建后立刻用其成功读取频道列表。
- **SC-002**: 开放接口的频道列表与节目单响应中,任意字段都不泄露上游播放地址或运维状态(零泄露)。
- **SC-003**: 一把被禁用或吊销的 key,其失效对正在使用它的客户端在"下一次请求"时即生效(无需等待或重启)。
- **SC-004**: 第三方开发者无需联系维护者、仅凭交互式文档与机器可读规范即可完成一次成功的开放接口调用。
- **SC-005**: 单把失控 key 的高频调用不会影响其他 key 的正常访问,也不会拖慢后台管理操作。
- **SC-006**: 后台管理员登录态无法访问任何开放接口,API key 无法访问任何后台管理接口(双向零穿透)。

## Assumptions

- 开放接口的数据源复用系统已整理后的对外输出层(归一化频道 + 已绑定 EPG 的节目),不新建并行数据源,也不读取上游原始导入数据。
- 现有后台管理用的对外输出路由(`/output/*` 及频道/节目单原始数据路由)在本次特性中**保持不变**,开放接口是并行的、独立的对外入口。
- 外部消费方需要自行保管明文 API key;系统不提供明文找回,丢失只能重新签发。
- 凭据以"平台签发的访问密钥"模型管理(管理员统一签发与吊销),首版不实现按用户绑定、多租户或细粒度频道可见性(预留作用域字段供未来扩展)。
- 首版的调用频率限制采用进程内简易实现,足以保护单实例部署;分布式限流留待后续。
- 接口契约采用"代码优先"方式产出:接口先以带文档注解的方式实现,再自动生成 OpenAPI 规范与交互文档,而非手写规范文件。
- 现有的审计、请求链路、错误响应等基础设施将被复用,不重新造轮子。
- Android TV 等专用客户端协议(设备配对、播放决策、自动换线等)是独立的、更窄的特性,不在本次开放平台范围内;本次只提供通用只读数据接口。
