# Feature Specification: 重构登录页面 UI

**Feature Branch**: `001-redesign-login-ui`

**Created**: 2026-07-20

**Status**: Draft

**Input**: User description: "重构登录页面的UI"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员完成登录并进入后台 (Priority: P1)

管理员（唯一身份角色）打开 `/login` 页面，输入正确的用户名与密码，提交后系统验证通过，用户被引导至原回调地址或默认后台首页。这是登录页存在的根本理由；如果这条流程不通，页面就失败了。

**Why this priority**: 登录是进入整个 MAGI 后台的唯一入口；此故事不通过则其他所有页面都访问不到。这是 P1 中不可妥协的核心。

**Independent Test**: 在已部署环境里访问 `/login`，用现有 admin 凭据登录，验证跳转至 `/dashboard`；可独立完成、独立验证、不依赖其他用户故事。

**Acceptance Scenarios**:

1. **Given** 用户未登录且数据库中存在 admin 账号，**When** 用户访问 `/login` 并提交正确用户名与密码，**Then** 页面在 1 秒内反馈"登录成功"并跳转至 `callbackUrl`（默认 `/dashboard`），URL 栏地址变化，刷新后仍保持登录态。
2. **Given** 用户已登录，**When** 用户再次访问 `/login`，**Then** 用户被自动重定向至 `/dashboard`，不再展示登录表单。
3. **Given** 用户未登录且从某个深层页面（如 `/channels`）被重定向至 `/login`，**When** 用户登录成功，**Then** 用户被引导回原 `/channels` 而非默认 `/dashboard`。

---

### User Story 2 - 登录失败时给出明确反馈 (Priority: P2)

用户提交了错误凭据（用户名不存在、密码错误、或服务端临时不可用）时，登录页必须给出清晰、可见、位于表单附近的错误提示，且不泄露"是用户名错还是密码错（避免账号枚举）"。

**Why this priority**: 登录失败的反馈直接影响管理员能否快速恢复（输错密码很常见），但相较于 P1（根本登录流程）属次级。

**Independent Test**: 故意输错密码提交，验证错误提示出现且文案与"用户名或密码错误"一致（不区分两类错误），表单保留用户名、清空密码、允许重试。

**Acceptance Scenarios**:

1. **Given** 用户提交了不匹配的用户名/密码组合，**When** 后端返回认证失败，**Then** 页面在表单附近（非仅顶部 toast）显示一条错误提示，文案为"用户名或密码错误"，密码字段清空，光标自动聚焦到密码字段。
2. **Given** 用户提交后后端连接超时或返回 5xx，**When** 错误发生，**Then** 页面显示"登录暂时不可用，请稍后重试"，登录按钮恢复可点击状态。
3. **Given** 用户上一次提交失败后再次提交正确凭据，**When** 提交成功，**Then** 错误提示立刻消失，页面跳转至回调地址。

---

### User Story 3 - 重构后视觉与项目宪法锁定的设计语言一致 (Priority: P3)

重构后的登录页必须遵循项目宪法（v2.2.0）中锁定的视觉语言与组件库 — 不再使用宪法禁用的旧前端 UI 栈。页面要与企业级后台管理系统的视觉气质一致：克制、确定、信息密度合理。

**Why this priority**: 这是"重构"本身的核心动机。但只要 P1/P2 功能正常，登录页"长得不一样"不会阻塞业务，所以放在 P3。

**Independent Test**: 在浏览器打开 `/login`，肉眼对比 antd 官方 v6 默认主题示例（如 antd 官网 ProTemplates）与本项目其他后台页面，确认登录页与项目其余页面的圆角、间距、字号、配色、按钮形态一致。

**Acceptance Scenarios**:

1. **Given** 项目宪法 v2.2.0 锁定视觉语言 X 与组件库 Y，**When** 开发者打开重构后的 `/login` 源码，**Then** 源码中不出现宪法禁用的旧栈关键字（旧 utility-first 样式框架、旧复制源码型组件库），所有视觉决策（颜色/间距/圆角/字号）均按 X 的 token 而非硬编码。
2. **Given** 重构后的登录页与项目其他后台页面（如 `/dashboard`、`/channels`）在同一个浏览器窗口对比，**When** 观察者对比两者的圆角、按钮形态、输入框样式、字体、配色，**Then** 视觉风格一致、无明显割裂。
3. **Given** 用户在 1440×900 桌面浏览器与 375×812 移动浏览器两种尺寸下访问 `/login`，**When** 观察布局，**Then** 表单在两种尺寸下均完整可见、可交互、无横向滚动条。

---

### Edge Cases

- 用户启用了浏览器自动填充密码管理器（如 1Password、Chrome 自动填充）时，表单字段必须能正确接收自动填充值，不被遮挡或样式破坏。
- 用户在提交过程中触发浏览器原生返回/前进按钮，登录请求结果应被妥善处理（避免重复提交、避免跳转到错误中间状态）。
- 用户连续快速点击登录按钮：在 pending 状态下按钮必须禁用，避免重复提交。
- 用户在登录态被后端意外失效（session 过期）后访问 `/login`：与未登录用户相同流程，无额外提示需求。
- 浏览器禁用 JavaScript：不在本特性范围内（项目整体为 SPA，登录页依赖 JS 是既定前提）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 登录页 MUST 提供用户名输入框、密码输入框（带可见性切换）、登录按钮三件套，且只有这三件套是登录的必填交互元素。
- **FR-002**: 登录页 MUST 沿用项目既有的用户名+密码认证契约（不在本次重构中新增 OAuth/SSO/邮箱登录/双因子认证等新认证方式）。
- **FR-003**: 提交时前端 MUST 做最小校验（用户名与密码均非空），校验失败时在对应字段下方就地提示，不发起网络请求。
- **FR-004**: 认证失败时（凭据错误、网络错误、服务端错误）MUST 在表单附近显示一条错误提示；凭据错误与系统错误的文案必须区分；凭据错误文案 MUST NOT 泄露"用户名错"还是"密码错"。
- **FR-005**: 登录成功后 MUST 跳转至 `callbackUrl` 查询参数（若存在且为站内地址）或 `/dashboard`（默认）；MUST 使用 replace 而非 push，避免"返回键又回到登录页"。
- **FR-006**: 已登录用户访问 `/login` MUST 被重定向至 `/dashboard`，不展示登录表单。
- **FR-007**: 登录按钮在提交中 MUST 显示加载状态并禁用，避免重复提交；提交结束（成功或失败）后 MUST 恢复可点击。
- **FR-008**: 登录页 MUST 遵循项目宪法 v2.2.0 锁定的视觉语言（含颜色、排版、4px 网格、圆角、动效 token）与组件库；MUST NOT 使用宪法禁用的旧前端 UI 栈（旧 utility-first 样式框架、旧复制源码型组件库）。
- **FR-009**: 登录页 MUST 在桌面（≥ 1280px）与移动（≥ 360px）两个断点下完整可用、无横向滚动。
- **FR-010**: 登录页 MUST 在表单附近显示项目标识（"MAGI" 字样 + 标识图形），让用户确认所在站点正确。
- **FR-011**: 错误提示、成功反馈 MUST 同时满足视觉无障碍（不依赖纯颜色传达信息，有文字说明）。

### Key Entities *(include if feature involves data)*

本特性为纯前端 UI 重构，不引入新数据实体。沿用既有实体：

- **User**: 既有的管理员账户实体（含用户名、密码哈希等）。本特性不修改其字段或契约。
- **Session**: 既有的登录会话实体。本特性不修改其生命周期。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户在键盘上完成一次完整登录（用户名 → Tab → 密码 → Enter）耗时 ≤ 10 秒（不含网络等待）。
- **SC-002**: 登录提交后用户看到结果（成功跳转或失败提示）的等待时间 ≤ 1 秒（不含网络往返，仅含前端渲染）。
- **SC-003**: 重构后的登录页源码中，宪法 v2.2.0 禁用的旧前端 UI 栈关键字出现次数 = 0（通过项目代码审查清单可验证）。
- **SC-004**: 重构后的登录页在桌面（1440×900）与移动（375×812）两个断点下，通过行业标准的可访问性自动化审计（如 WCAG 2.1 AA 级自动检查）无严重违规。
- **SC-005**: 错误反馈对最终用户而言"可理解且可操作"（即用户读到提示后知道下一步该做什么）— 通过 1 名真实管理员在 5 次故意输错的测试中 100% 能说出"我需要重新输入密码"或"我需要稍后重试"的判断来验证。
- **SC-006**: 重构后的登录页与 **antd v6 官方示例**（官网 Form 组件文档、ProTemplates）在 5 名内部观察者的"一致性盲测"中，≥ 4 人认为登录页"明显属于同一设计语言"。**注**：本特性 scope 不要求与项目其他后台页（仍处宪法 v2.0.0 迁移待办中、保留旧 shadcn 栈）视觉一致 —— 待整体迁移完成后，可在独立特性中验收跨页一致性。

## Assumptions

- 后端认证契约（用户名+密码、`signIn.username`、callbackUrl 跳转协议）保持不变；本特性不触及后端代码。
- 现有 `apps/web` 已有路由（TanStack Router）与认证客户端（`@/lib/auth-client`）的接线方式不变；重构仅替换登录页的视觉与组件实现，不替换路由/状态/数据获取层。
- 项目宪法 v2.2.0 锁定的视觉语言是本次重构的唯一视觉契约来源；规划阶段需在读 antd v6 design.md 后输出具体设计稿（颜色/字号/圆角 token 选择），但 spec 阶段不预设具体值。
- 默认布局采用"单列居中"（表单水平居中、最大宽度受限），符合企业级后台管理系统的克制气质；如规划阶段证明双列布局（左 hero + 右表单）显著更好，可在 plan 中调整，但需说明理由。
- "忘记密码"、"注册账号"、"记住我"、"切换主题"等功能不在本次重构范围内。
- 国际化（i18n）不在本次重构范围内；登录页文案使用与现状一致的简体中文。
- 浏览器范围：现代版 Chrome / Edge / Safari / Firefox（最新两个稳定版本），不在本特性中支持 IE 或已停更浏览器。
- 视觉与无障碍冲突时（如颜色对比度），优先遵循 antd v6 design.md 的"Do's and Don'ts"章节指引，必要时通过 token 覆盖而非自定义 CSS 解决。
