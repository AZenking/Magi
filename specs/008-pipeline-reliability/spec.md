# Feature Specification: 数据管线可靠性与播放反馈闭环

**Feature Branch**: `008-pipeline-reliability`

**Created**: 2026-08-04

**Status**: Draft

**Input**: User description: "修复端到端业务流程中的 5 个卡点：定时同步任务失效、canonical 生成耦合 EPG 匹配、Safe Operations worker 空壳、TV 播放失败不上报、服务端自动换线引擎未接线。"

## Scope & Boundaries

本特性修复当前数据管线（数据源同步 → 输出频道编排 → 播放决策 → 客户端播放）中的 5 个断裂点，使从"添加数据源"到"在电视上稳定播放"的端到端流程可以自动、可靠地跑通，且服务端能基于真实播放结果优化线路健康度与主备切换决策。

**In scope**:

- 修复定时同步任务，使其能遍历所有已启用的源（而不是因 null 标识符必然失败）。
- 在 M3U 同步完成后自动生成或更新输出频道，不再强制要求用户先手动触发 EPG 匹配才能看到频道。
- 将 Safe Operations 的 worker 执行端从空壳替换为真正的预览→应用→恢复流程，使"预览无副作用、应用有变更集、可回滚"的契约生效。
- 新增 TV 播放失败/换线结果上报接口，让服务端线路健康度能纳入真实客户端播放结果。
- 将已实现但未接线的线路故障转移引擎接入线路检测后的处理流程，使主线路持续失败时服务端能自动切换主备标记。

**Out of scope**:

- 收藏、最近观看、播放历史等用户状态功能（路线图 V0.3）。
- DVR、时移、Catch-up 和多画面等高级播放功能。
- 频道搜索、多日 EPG 时间轴和节目提醒。
- 重新设计 EPG 匹配算法本身（保留现有匹配逻辑，仅修复触发时机）。
- 多用户家庭成员档案和并发播放限制。
- 新增前端管理页面（复用现有的源管理、输出频道和运营工作台页面）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 同步后自动看到输出频道 (Priority: P1)

作为系统管理员，我希望添加 M3U 源并同步后立即在输出频道列表中看到频道，定时同步也能自动运行，而不需要手动触发 EPG 匹配才能生成输出数据。

**Why this priority**: "同步了但看不到频道"是当前最严重的体验断裂。canonical_channels 的生成完全依赖 EPG 匹配，而 EPG 匹配只能手动触发——这意味着每个新源都需要用户知道"还要再点一次 EPG 匹配"。同时定时同步任务因标识符传递错误而必然失败，所有自动同步形同虚设。

**Independent Test**: 创建一个 M3U 源并同步；验证同步完成后输出频道列表中已有频道（即使尚未执行任何 EPG 匹配）。再验证定时同步任务能遍历所有源并成功执行。

**Acceptance Scenarios**:

1. **Given** 系统中没有任何输出频道，**When** 管理员创建一个 M3U 源并触发同步，**Then** 同步完成后输出频道列表中出现该源的频道，每条频道至少有一条播放线路，且频道名称、分组和台标来自源数据。
2. **Given** 已有一个已同步的 M3U 源，**When** 管理员后续触发 XMLTV 同步和 EPG 匹配，**Then** 输出频道的 EPG 绑定被补充，但既有的频道身份、人工覆盖和线路信息不被破坏。
3. **Given** 系统配置了定时同步间隔，**When** 定时器触发，**Then** 所有已启用的源按其类型逐一同步，不会因缺少源标识符而失败或跳过。
4. **Given** 定时同步正在运行，**When** 管理员手动触发某个特定源的同步，**Then** 手动任务正常排队执行，不与定时任务产生冲突或重复写入。
5. **Given** 一个源在上游新增了频道，**When** 定时同步完成，**Then** 新频道出现在输出列表中，且既有频道的人工配置（名称覆盖、台标、主备线路、健康历史）保持不变。
6. **Given** 一个源在上游删除了频道，**When** 定时同步完成，**Then** 被删除的频道在输出列表中被标记为失效或移除，其人工配置被保留以便后续恢复或清理决策。

### User Story 2 - 安全操作预览与回滚生效 (Priority: P2)

作为系统管理员，我希望在执行同步或 EPG 匹配前看到真实的影响预览，确认后变更才生效，且发现结果不符合预期时可以回滚到操作前状态。

**Why this priority**: Safe Operations 的 API 端和 Web UI 已经完整实现了"预览→批准→应用→恢复"的流程，但 worker 执行端全是空壳——预览阶段就直接执行了副作用操作，应用阶段什么都不做。这导致"安全预览"承诺是虚假的，用户无法信任预览结果。

**Independent Test**: 发起一次源同步的安全操作；验证预览阶段不改变任何输出数据，预览中展示的频道变更数量与实际应用后的变更数量一致，且应用后可以通过恢复点回滚到操作前状态。

**Acceptance Scenarios**:

1. **Given** 管理员发起一次同步安全操作，**When** 预览阶段完成，**Then** 预览展示新增、更新、失效和受影响人工配置的数量，且当前输出频道列表未发生任何变化。
2. **Given** 预览已生成，**When** 管理员批准应用，**Then** 变更集中记录的所有变更被原子应用，输出频道列表更新到新状态，操作被审计记录。
3. **Given** 应用已完成，**When** 管理员发现结果不符合预期并选择恢复，**Then** 系统使用恢复点将频道及其运营配置回滚到操作前的一致状态。
4. **Given** 同一范围的安全操作正在运行，**When** 管理员再次发起相同范围的操作，**Then** 系统阻止重复执行并提示当前正在运行的任务。
5. **Given** 预览阶段或应用阶段发生失败，**When** 错误被捕获，**Then** 所有已执行的变更被回滚，输出状态保持一致，管理员收到明确的失败原因。

---

### User Story 3 - 播放结果回馈与健康线路切换 (Priority: P2)

作为电视观众，我希望主线路播放失败时播放器能自动切换到备线路，并且我的播放失败经历能帮助服务端优化未来所有人的线路选择；作为管理员，我希望主线路持续不健康时服务端能自动将备线路提升为主线路。

**Why this priority**: 当前 TV 端的本地换线已实现，但失败信息永远不回传服务端；服务端的线路健康度完全依赖主动探测，与真实播放体验可能脱节。同时，服务端的自动主备切换引擎已完整实现但从未被调用，"主线路失效自动切备线路"这个核心差异化能力未闭环。

**Independent Test**: 在 TV 上播放一个有多条线路的频道；模拟主线路播放失败，验证 TV 本地切换到备线路并上报失败结果；再验证服务端收到上报后更新该线路的健康度；最后验证主线路持续失败超过阈值后服务端自动将备线路提升为主线路。

**Acceptance Scenarios**:

1. **Given** 一台已授权的 TV 正在播放某频道的主线路，**When** 该线路播放失败（如连接超时、HTTP 错误或解码失败），**Then** TV 自动尝试下一条线路，并在后台向服务端上报该线路的失败类型和已播放时长。
2. **Given** TV 上报了某线路的播放失败，**When** 服务端处理上报，**Then** 该线路的健康度被更新（失败次数、失败类型和最后失败时间），且更新结果影响后续播放决策的线路排序。
3. **Given** 一条主线路连续失败次数达到故障转移策略配置的阈值，**When** 线路检测或播放失败上报处理完成后，**Then** 服务端自动将该线路的备线路提升为新的主线路，并记录切换原因。
4. **Given** 一条被降级的线路恢复健康（连续成功次数达到恢复阈值），**When** 线路检测完成，**Then** 服务端考虑是否将其恢复为可用线路或主线路，受冷却期策略约束。
5. **Given** TV 上报播放结果时网络不可用，**When** 上报请求失败，**Then** TV 在本地暂存上报数据并在网络恢复后重传，不影响当前播放体验。
6. **Given** 服务端收到大量播放失败上报，**When** 处理频率超过系统保护阈值，**Then** 系统对同一线路的重复上报进行去重或限频，不产生重复健康度更新或请求风暴。

### Edge Cases

- 定时同步执行时，某源的上游服务器不可达：该源的同步标记为失败并记录原因，不影响其他源的同步，下次定时继续重试。
- 同一源被定时同步和手动同步同时触发：系统通过幂等性或互斥锁保证不会产生重复写入或数据竞争。
- M3U 源没有关联任何 XMLTV 源：输出频道仍然生成（无 EPG 绑定），频道名称和分组来自 M3U 数据。
- 源中频道数量非常大（超过数万条）：同步、归一化和输出查询不会被静默截断，而是分批处理或明确分页。
- 安全操作恢复点因数据量过大导致回滚耗时很长：系统提供进度反馈且不阻塞其他管理操作。
- TV 上报的线路标识符在服务端已不存在（如线路被管理员删除）：服务端安全忽略该上报，不抛出未处理错误。
- 线路故障转移策略未配置：系统使用安全的默认阈值，不会因缺少配置而跳过自动切换或频繁切换。
- 多台 TV 同时上报同一线路的失败：服务端正确聚合失败信息，不会因并发上报导致健康度计算错误或重复切换。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在 M3U 源同步完成后，自动根据源数据生成或更新输出频道（包括频道身份、名称、分组和播放线路），无需用户手动触发 EPG 匹配。
- **FR-002**: 系统 MUST 保留输出频道在历次同步中的人工配置（名称覆盖、台标覆盖、分组覆盖、主备线路标记、EPG 绑定锁定、可见性和健康历史），同步不得破坏这些配置。
- **FR-003**: 系统 MUST 在定时同步触发时遍历所有已启用的源并按类型执行同步，不得因缺少源标识符而跳过或失败。
- **FR-004**: 系统 MUST 在定时同步中记录每个源的同步结果（成功或失败及原因），并在部分源失败时继续同步其他源。
- **FR-005**: 系统 MUST 为 M3U 同步生成的输出频道自动选择一条播放线路作为主线路；当源数据指定了主线路时优先尊重源数据。
- **FR-006**: EPG 匹配 MUST 能为已有输出频道补充 EPG 绑定，且不得删除已有的人工锁定绑定。
- **FR-007**: Safe Operations 的预览阶段 MUST NOT 产生任何数据副作用；预览结果 MUST 准确反映应用阶段将发生的变更。
- **FR-008**: Safe Operations 的应用阶段 MUST 在单个原子事务中执行变更集，并在失败时完整回滚。
- **FR-009**: Safe Operations MUST 为每次应用创建恢复点，记录操作前的频道和配置状态，使管理员能回滚到操作前状态。
- **FR-010**: 系统 MUST 提供一个面向已授权客户端的播放结果上报接口，接受线路标识符、失败类型、播放时长和客户端上下文。
- **FR-011**: 播放结果上报 MUST 更新对应线路的健康度（失败次数、失败类型、最后失败时间和最后成功时间），且更新结果 MUST 影响后续播放决策的线路排序。
- **FR-012**: 系统 MUST 在线路连续失败次数达到故障转移策略阈值时，自动将该线路的备线路提升为主线路，并记录切换原因和时间。
- **FR-013**: 系统 MUST 在线路恢复健康（连续成功达到恢复阈值）后，在冷却期约束下考虑恢复其可用性或主线路地位。
- **FR-014**: 播放结果上报接口 MUST 对同一线路的重复或高频上报进行去重或限频，不得产生重复健康度更新。
- **FR-015**: TV 客户端 MUST 在播放失败后本地暂存上报数据，并在网络恢复后自动重传，上报失败 MUST NOT 影响当前播放或换线体验。
- **FR-016**: 所有同步、安全操作、播放上报和线路切换事件 MUST 产生结构化审计或日志记录，包含链路标识符，且不得暴露播放地址或凭据。
- **FR-017**: 系统 MUST 在线路检测（主动探测）和播放上报（被动反馈）两种健康度信号之间建立一致的合并规则，两种信号共同决定线路的最终健康状态。

### Key Entities *(include if feature involves data)*

- **Sync Job Result**: 代表一次定时或手动同步中单个源的执行结果；包含源标识符、源类型、成功或失败状态、失败原因、处理的频道数量和执行时间。用于定时同步的批量结果汇报。
- **Playback Report**: 代表一次客户端播放尝试的结果；包含目标线路标识符、频道标识符、失败类型（连接超时、HTTP 错误、解码失败等）、已播放时长、客户端标识符和时间戳。不含播放地址或凭据。
- **Line Health Snapshot**: 代表一条播放线路在某一时刻的综合健康状态；由主动探测结果和被动播放上报合并得出；包含在线状态、连续失败次数、连续成功次数、最后检测时间和最后播放失败时间。
- **Failover Decision**: 代表一次自动主备线路切换决策；包含目标频道、原主线路、新主线路、触发原因（探测失败或播放上报累积）、决策时间和关联策略配置。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员添加 M3U 源并同步完成后，100% 的情况下无需额外操作即可在输出频道列表中看到频道。
- **SC-002**: 配置了定时同步的环境下，95% 的已启用源在定时同步后保持与上游一致（新增频道出现、失效频道标记），定时同步任务本身的失败率为 0%。
- **SC-003**: 连续 3 次定时同步后，既有频道的人工配置（名称、台标、主备线路、健康历史）零丢失。
- **SC-004**: 安全操作预览阶段对输出频道数据的变更数为 0；应用阶段实际变更数与预览一致率达到 100%。
- **SC-005**: 安全操作应用失败时，100% 的变更被回滚，输出状态与操作前完全一致。
- **SC-006**: TV 主线路播放失败后，95% 的情况下在 6 秒内完成备线路切换且上报失败结果到服务端。
- **SC-007**: 主线路连续失败达到阈值后，服务端在 2 分钟内自动完成主备线路切换，且新主线路在下次播放决策中排在第一位。
- **SC-008**: 线路健康度同时纳入主动探测和客户端上报两种信号后，播放决策中"推荐的第一条线路实际可用率"不低于 95%。
- **SC-009**: 10 台 TV 同时上报同一线路失败的并发场景下，不出现重复健康度更新或重复主备切换，正确率达到 100%。

## Assumptions

- 现有的数据源同步（M3U/XMLTV 下载、解析、写入原始表）逻辑正确且可用；本特性修复的是同步后的自动编排和触发时机，不重写解析逻辑。
- 现有的频道归一化、合并和覆盖逻辑（当前在 EPG 匹配处理器中实现）是正确的；本特性将其从 EPG 匹配中解耦，使其在 M3U 同步后也能独立运行，但不改变归一化算法本身。
- 现有的 Safe Operations API 端（控制器、application use case、变更集和恢复点数据模型）已经完整且可用；本特性修复的是 worker 执行端，使其对接已有的 API 契约。
- 现有的线路故障转移策略模型（`ChannelFailoverPolicy`）和故障转移评估引擎（`EvaluateStreamFailoverUseCase`）已经完整实现且逻辑正确；本特性将其接入线路检测和播放上报的处理流程。
- TV 客户端的本地换线逻辑（`Media3PlaybackSession`）已经可用；本特性在其基础上增加失败结果上报，不改变换线决策本身。
- 线路检测（worker 的主动探测）继续按现有调度运行；本特性不改变探测频率，而是将探测结果与播放上报合并。
- 定时同步的间隔由环境变量控制（如已有的 `SCHEDULE_SYNC`），本特性修复遍历逻辑而非调度机制本身。
- 本特性不新增前端管理页面；管理员通过现有的源管理、输出频道和运营工作台页面观察结果。
