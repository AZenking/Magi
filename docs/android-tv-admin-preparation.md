# Android TV 建设前的管理端准备清单

> 文档状态：规划与进度评估  
> 更新日期：2026-07-28  
> 适用范围：以 Magi Server 为后台的 Android TV 直播客户端  
> 本文只描述管理端与服务端准备，不涉及 Android 端代码实现。

## 1. 结论

当前 Magi 已经具备“直播源聚合与运维后台”的主体能力，但还不具备完整的“Android TV 客户端运营平台”。

- 如果 TV 端只是读取 M3U/XMLTV，准备量较小。
- 如果 TV 端需要成为可分发、可升级、可长期运营的正式产品，还需要补齐客户端 API、设备鉴权、版本管理、远程配置、用户数据和客户端可观测性。

在 Android TV 开发启动前，管理端至少应先明确并冻结以下边界：

1. TV 是局域网自用播放器，还是面向多用户分发的产品。
2. TV 是否只提供直播，首版是否排除点播、录播和时移。
3. TV 如何绑定 Magi Server，以及是否允许匿名访问。
4. 播放地址由 TV 直连上游，还是由 Magi 代理或签名后下发。
5. App 通过 Google Play 更新，还是由管理端提供 APK 侧载更新。

## 2. 当前已经具备的基础

Magi 当前已经拥有以下能力：

- M3U/XMLTV 数据源同步。
- 频道归一化、分组、频道号、台标和 EPG。
- 一个频道关联多条播放线路。
- 主线路、备用线路、线路排序和故障切换策略。
- 播放线路健康检查。
- 频道隐藏、停用、删除等生命周期管理。
- 频道搜索和分组过滤。
- Legacy M3U/XMLTV 输出。
- 面向 Magi TV 的 V2 M3U/XMLTV 输出。
- V2 M3U/XMLTV 使用稳定的 `magi:{canonicalChannelId}` 关联频道和节目。
- V2 M3U 根据线路健康状态、主线路标记、线路顺序和响应时间选择当前最佳线路。
- 统一节目单查询，支持频道、分组、搜索、状态和最长七天时间范围。
- EPG 未匹配、冲突、来源过期、空节目单、节目缺口和节目重叠检测。
- 管理端输出地址页面，区分 Legacy 与 Magi TV V2 地址。
- 后台账号登录、任务队列、审计、备份和运行状态监控。

## 3. P0：Android TV 开发前必须准备

### 3.1 独立的 TV 客户端 API

当前已经具备以下输出协议雏形：

- `GET /output/v2/m3u`
- `GET /output/v2/xmltv`
- `GET /output/guide`
- `GET /output/groups`
- `GET /output/channels`
- `GET /output/channels/{id}`

其中：

- V2 M3U/XMLTV 使用相同的稳定 `magi:{canonicalChannelId}`。
- 节目单接口支持时间范围、频道、分组、搜索、状态和分页。
- 频道接口已经包含标准名称、分组、台标、频道号和 EPG 绑定信息。

但这些接口仍属于管理接口，并整体受后台 Session 登录保护。Android TV 不应直接复用管理员会话，也不应获得同一个控制器中的频道编辑、线路编辑和生命周期操作权限。

下一步应在现有输出用例之上建立独立、只读、版本化的客户端 API，例如：

- `GET /api/tv/v1/bootstrap`
- `GET /api/tv/v1/groups`
- `GET /api/tv/v1/channels`
- `GET /api/tv/v1/channels/{id}`
- `GET /api/tv/v1/epg`
- `GET /api/tv/v1/search`
- `POST /api/tv/v1/playback/{channelId}`
- `POST /api/tv/v1/playback/{channelId}/failure`

现有 V2 M3U/XMLTV 可以继续作为成熟 IPTV 播放器的兼容输出；原生 Magi TV 应优先使用结构化 TV API。

客户端接口应直接返回 TV 所需的数据：

- 首页分组和排序。
- 频道号、名称、台标和分组。
- 当前节目和下一个节目。
- 频道是否可播放。
- 最终播放端点。
- 配置版本和缓存有效期。

TV 不应负责拼装多个管理接口，也不应获得频道编辑、数据源管理、任务管理等权限。

API 契约还应统一：

- API 版本策略。
- 时间和时区格式。
- 分页规则。
- 错误码。
- 缓存、ETag 和增量刷新规则。
- 向后兼容周期。
- 请求限流和超时策略。

### 3.2 TV 设备鉴权

当前鉴权以后台 Web 会话为中心，主要通过 Session Cookie 判断登录状态，尚未区分管理员、普通用户和 TV 设备。

TV 端应选择明确的设备鉴权模式：

- 家庭自用：设备显示配对码或二维码，由已登录管理端确认绑定。
- 多用户产品：采用手机扫码登录或设备授权流程。
- 局域网匿名使用：仍建议签发设备令牌，以便吊销、限流和统计。

建议的配对流程：

1. TV 创建一次性配对请求。
2. 服务端返回短时有效的六位码和二维码内容。
3. 用户在 Web 管理端确认设备。
4. TV 轮询配对结果。
5. 配对成功后获得长期设备令牌和刷新凭据。
6. 管理端可以随时解绑设备或吊销令牌。

安全边界：

- 管理员令牌和设备令牌必须分离。
- 设备令牌只允许访问 TV 客户端 API。
- 配对码必须短时有效、一次性使用并限制尝试次数。
- 令牌应支持过期、轮换和吊销。
- 播放地址不应作为长期静态凭据暴露。

### 3.3 播放地址交付与换线策略

当前已经完成的基础：

- V2 M3U 仅输出处于有效生命周期且允许输出的频道。
- 过滤不允许参与输出或不允许故障切换的线路。
- 排除当前不可用的线路。
- 按健康状态、主线路标记、线路顺序和响应时间选择最佳线路。
- `mode=all` 可以输出全部当前可用线路。

这些能力解决了“生成列表时选择最佳线路”的问题，但尚未形成“播放期间的设备级播放会话与失败换线协议”。

管理端需要明确 TV 最终取得的播放资源形式：

- TV 直接访问上游地址。
- Magi 返回短期签名地址。
- Magi 作为播放代理。
- 根据频道和设备动态选择当前最优线路。

播放接口至少应处理：

- HLS、MPEG-TS、DASH 等流格式。
- 上游所需的 Header、Cookie、User-Agent 和 Referer。
- 播放地址有效期。
- 连接和首帧超时。
- 主线路失败后的备用线路选择。
- 同一失败线路的冷却时间。
- TV 播放失败上报。
- 服务端返回下一条线路。
- 所有线路失败时的统一错误状态。

建议让 TV 只获取“当前可播放端点”，主备线路、上游凭据和源管理细节继续保留在服务端。

当前 V2 M3U 仍直接输出上游 `streamUrl`，因此短期签名地址、播放代理、上游特殊请求头、安全隔离和播放失败后的动态换线仍属于待建设项。

### 3.4 TV 启动配置与远程配置

管理端需要新增客户端配置发布能力。TV 启动时通过 `bootstrap` 一次获取：

- API 和静态资源地址。
- 首页分组和默认频道。
- EPG 时间窗口和刷新周期。
- 播放超时、重试和换线策略。
- 台标占位资源。
- 功能开关。
- 维护状态和公告。
- 最低支持版本和推荐版本。
- 配置版本、发布时间和缓存有效期。

管理端应支持：

- 配置草稿。
- 发布前预览和校验。
- 正式发布。
- 灰度发布。
- 历史版本查询。
- 一键回滚。

TV 应能缓存最近一次有效配置，在服务短时不可用时降级启动。

### 3.5 Android TV 版本管理

管理端需要建立客户端版本和发布管理能力：

- `versionCode`。
- `versionName`。
- APK 或应用商店下载地址。
- 文件大小和 SHA-256 校验值。
- 更新说明和发布日期。
- 最低兼容版本。
- 推荐版本。
- 强制更新或可选更新。
- 发布渠道和灰度范围。
- 支持的 Android 版本和 CPU ABI。
- 发布暂停、撤回和回滚。

如果使用 Google Play，管理端仍需管理最低支持版本和强制升级策略。

如果采用 APK 侧载，还需要：

- 可靠的安装包存储。
- HTTPS 下载。
- APK 签名管理。
- 完整性校验。
- 下载鉴权。
- 安装失败诊断。

## 4. P1：建议与首版同步完成

### 4.1 设备管理

管理端应提供设备列表和设备详情，至少记录：

- 设备 ID 和用户自定义名称。
- 设备型号、厂商和 Android 版本。
- App 版本。
- 首次绑定和最后在线时间。
- 所属用户或家庭。
- IP、网络类型和时区。
- 当前配置版本。
- 最近一次播放时间。
- 启用、禁用、解绑和令牌吊销状态。

建议支持以下操作：

- 修改设备名称。
- 解绑设备。
- 禁用或重新启用设备。
- 吊销并重新签发令牌。
- 查看 App 和配置版本。
- 查看最近错误和播放诊断。

### 4.2 面向 TV 的频道编排

现有频道分组主要来自上游数据。正式 TV 首页还需要单独的运营编排能力：

- TV 分组名称和排序。
- 分组内频道排序。
- 频道号。
- 首页推荐和置顶。
- TV 可见性。
- 默认开机频道。
- 上下架时间。
- 地区、语言、设备或用户分群可见性。
- 成人内容和家长控制标记。

现有 `hidden`、`starred`、`standardGroup`、`channelNumber` 可以作为基础，但应避免把“管理员收藏”“客户端推荐”和“用户收藏”混为同一含义。

### 4.3 用户和观看状态

当前认证数据以后台用户为主，没有完整的 TV 设备和观看状态模型。

根据首版范围，可以准备：

- 收藏频道。
- 最近观看。
- 上次播放频道。
- 用户自定义频道排序。
- 家长锁和 PIN。
- 多用户档案。
- 跨设备同步。

如果首版只面向家庭直播，可以先实现设备级收藏和最近观看，暂不建设复杂会员体系。

### 4.4 客户端可观测性

当前服务端已经具备数据源同步、任务和线路健康监控，但还需要补充真实 TV 播放体验数据：

- App 启动成功率和启动耗时。
- 配置拉取成功率。
- 播放成功率。
- 点击频道到首帧的耗时。
- 卡顿次数和卡顿时长。
- 频道切换耗时。
- 播放错误类别和错误码。
- 实际选用的播放线路。
- App 版本、设备型号和网络类型。
- 崩溃和 ANR。

管理端应至少支持按以下维度查询：

- 时间范围。
- App 版本。
- 设备型号。
- 频道。
- 播放线路。
- 错误类型。

同时应明确隐私范围、数据保留期和脱敏规则，不采集不必要的个人信息或上游密钥。

## 5. P2：可在产品验证后建设

- 消息公告和维护通知。
- 多套远程配置和 A/B 实验。
- 客户端诊断日志上传。
- 远程清理缓存、刷新配置等设备指令。
- 多租户和家庭成员权限。
- 订阅套餐、频道授权和设备额度。
- DRM、地域限制和并发播放限制。
- CDN、转码、DVR、时移和 Catch-up。
- 多画面播放。

这些能力不应阻塞直播 MVP，除非商业模式或内容授权明确要求。

## 6. 推荐的最小闭环

正式开始 Android TV 产品开发前，管理端最好达到以下状态：

状态说明：

- ✅ 已具备
- 🟡 已具备基础，但尚未形成 TV 可直接使用的完整能力
- ⬜ 尚未建设

| 状态 | 能力 | 当前说明 |
|---|---|---|
| ✅ | 稳定频道标识 | V2 M3U/XMLTV 统一使用 `magi:{canonicalChannelId}` |
| ✅ | V2 M3U/XMLTV 输出 | 已区分 Legacy 与 Magi TV V2 输出 |
| ✅ | 服务端最佳线路选择基础 | 已按健康状态、主线路、顺序和响应时间选择 |
| ✅ | 统一节目单查询基础 | 支持时间范围、频道、分组、搜索、状态和分页 |
| 🟡 | 稳定、版本化的 TV 只读 API | 已有 V2 输出和节目单，但仍位于管理控制器并使用后台 Session |
| 🟡 | 播放接口返回当前可播放端点 | V2 M3U 会输出最佳线路，但仍直接暴露上游地址 |

## 7. 不同产品目标下的范围

### 7.1 局域网自用直播播放器

优先完成：

1. 独立 TV API。
2. 简化的设备令牌或配对。
3. Bootstrap 配置。
4. 播放端点和主备线路切换。
5. 基础设备列表和错误日志。

可以暂缓：

- 多用户体系。
- 商业订阅。
- 灰度版本发布。
- 复杂运营推荐。
- 跨设备状态同步。

### 7.2 可分发、可长期运营的正式产品

P0 和 P1 应在 TV 开发中期前完成，并额外确认：

- 隐私政策和数据保留策略。
- 应用签名和发布渠道。
- 服务条款和内容合规声明。
- 设备额度与滥用控制。
- API 限流和容量规划。
- 服务端与 TV 版本的兼容矩阵。

## 8. 建议实施顺序

1. 冻结产品边界和播放交付方式。
2. 定义 TV API、鉴权和错误码契约。
3. 实现设备配对和设备管理。
4. 实现 Bootstrap 与远程配置发布。
5. 实现播放决策、失败上报和备用线路协议。
6. 实现版本发布和最低版本控制。
7. 增加收藏、最近观看等用户状态。
8. 建立客户端可观测性和运营报表。

首个技术验证版可以只依赖前五项；面向用户发布前，应完成版本管理、设备管理和基础可观测性。
